# Just Do Testing Plugin SDK

[![CI](https://github.com/stasbykov/just-do-testing-plugin-sdk/actions/workflows/ci.yml/badge.svg)](https://github.com/stasbykov/just-do-testing-plugin-sdk/actions/workflows/ci.yml)
[![Java 21](https://img.shields.io/badge/Java-21-blue)](https://openjdk.org/projects/jdk/21/)

**Just Do Testing Plugin SDK** — открытый Java API для создания собственных **конструкторов объектов** в настольном приложении [Just Do Testing](https://github.com/stasbykov/just-do-testing).

Конструктор позволяет пользователю создавать объект через удобную форму вместо ручного редактирования JSON или текста. Разработчик конструктора определяет поля и их поведение, правила проверки, зависимости от другого объекта и способ формирования итогового тела. Пользователь настраивает объект в приложении, а затем использует его в тестовых сценариях с Kafka, REST и PostgreSQL.

Например, конструктор «Заказ» может предложить поля «Артикул» и «Количество», проверить значения и сгенерировать JSON для отправки. Более сложный конструктор может менять доступные поля и значения в зависимости от настроек другого объекта.

> SDK **не является отдельным приложением** и не выполняет тестовые сценарии самостоятельно. Он содержит контракты, по которым Just Do Testing загружает и вызывает пользовательские конструкторы. Код конкретного конструктора находится в отдельном JAR-плагине.

## Как это работает

У системы три части:

| Компонент | Ответственность |
| --- | --- |
| **Just Do Testing** | Отображает форму, хранит проекты, выбирает родительские объекты, запускает маршруты и сценарии, ведёт журнал и формирует Allure-отчёт. |
| **Plugin SDK** (этот репозиторий) | Предоставляет Java-интерфейсы `BuilderPlugin` и `ObjectBuilder`, описание полей `Field` и типы данных для взаимодействия с приложением. |
| **Ваш плагин** (отдельный JAR) | Описывает один или несколько типов объектов, форму их настройки, проверки, правила пересчёта и генерацию JSON/текста. |

Жизненный цикл конструктора:

1. При запуске приложение обнаруживает JAR через `META-INF/services` и метаданные манифеста.
2. При создании объекта вызывает `defaults()`, затем `form(...)`, чтобы показать форму.
3. При изменении пользователем поля или родителя повторно вызывает `form(...)`. Конструктор возвращает обновлённые настройки, набор полей и ошибки.
4. При предпросмотре или выполнении сценария приложение вызывает `generate(...)` и использует возвращённое тело в настроенном маршруте.

**Один JAR может предоставлять несколько типов объектов.** Типы определяются реализациями `ObjectBuilder`; список доступных типов возвращает одна реализация `BuilderPlugin`. Плагин описывает данные и правила, но **не создаёт JavaFX-экраны**, не управляет хранением проекта и не выполняет Kafka-, HTTP- или SQL-операции.

## Быстрый старт: готовый пример

Для знакомства с SDK не нужно сразу писать свой плагин. В репозитории есть рабочий пример [«Доставка»](examples/shipping-builder), который предоставляет два типа объектов:

- **Склад** — позволяет выбрать зону доставки.
- **Партия отправлений** — может ссылаться на «Склад», предлагает зависящие от него варианты доставки, поддерживает список мест, страховку и вычисление общего количества.

### 1. Получите JAR примера

Готовый плагин `shipping-builder.jar` можно взять в [GitHub Releases](https://github.com/stasbykov/just-do-testing-plugin-sdk/releases) (релиз `v1.0.0`).

Если хотите изучить исходники и собрать пример самостоятельно, понадобятся **JDK 21** и Maven **3.9+**. Maven Wrapper уже включён в репозиторий:

```bash
git clone https://github.com/stasbykov/just-do-testing-plugin-sdk.git
cd just-do-testing-plugin-sdk
./mvnw -f examples/shipping-builder/pom.xml clean verify
```

В Windows вместо `./mvnw` используйте `mvnw.cmd`. Результат сборки:

```text
examples/shipping-builder/target/shipping-builder.jar
```

Пример подключает **SDK 1.0.0 из Maven Central**. Отдельно собирать SDK не требуется.

### 2. Установите плагин в Just Do Testing

1. Запустите Just Do Testing и откройте **☰ → Модули… → Открыть каталог модулей**.
2. Скопируйте туда `shipping-builder.jar`.
3. Перезапустите приложение и проверьте наличие модуля «Доставка» в **☰ → Модули…**.
4. Создайте объект типа «Склад» и установите зону «Город».
5. Создайте «Партию отправлений», укажите склад в поле «Родительский объект» и проверьте доступные услуги.
6. Измените зону склада на «За городом»: форма партии обновит способ доставки и список услуг.
7. Добавьте две строки с количеством мест `2` и `3` — в сформированном JSON будет `"totalPieces":5`.

Исходники [`ShippingPlugin.java`](examples/shipping-builder/src/main/java/example/shipping/ShippingPlugin.java) показывают регистрацию двух типов, зависимую форму, массив строк и генерацию. [Тесты примера](examples/shipping-builder/src/test/java/example/shipping/ShippingPluginTest.java) демонстрируют проверку правил без запуска приложения.

## Создание собственного конструктора

Ниже — минимальный работающий пример **«Заказ»**. Он позволит создать объект с артикулом и количеством, проверить положительное количество и сгенерировать JSON с идентификатором.

### Шаг 1. Создайте отдельный Maven-проект

Рекомендуемая структура:

```text
order-builder/
├── pom.xml
└── src/
    └── main/
        ├── java/example/order/
        │   ├── OrderPlugin.java
        │   └── OrderBuilder.java
        └── resources/META-INF/
            ├── MANIFEST.MF
            └── services/
                └── io.github.stasbykov.justdotesting.plugin.BuilderPlugin
```

Пример `pom.xml`:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0">
    <modelVersion>4.0.0</modelVersion>
    <groupId>example.order</groupId>
    <artifactId>order-builder</artifactId>
    <version>1.0.0</version>

    <properties>
        <maven.compiler.release>21</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>io.github.stasbykov.justdotesting</groupId>
            <artifactId>scenario-plugin-api</artifactId>
            <version>1.0.0</version>
            <scope>provided</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
            </plugin>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-jar-plugin</artifactId>
                <version>3.4.1</version>
                <configuration>
                    <archive>
                        <manifestFile>src/main/resources/META-INF/MANIFEST.MF</manifestFile>
                    </archive>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>
```

**Почему `provided`?** Контракт SDK и Jackson уже предоставляются приложением. Их не нужно повторно упаковывать в плагин: так меньше риск несовместимых копий классов.

**Актуальная версия SDK — `1.0.0`.** Maven загрузит зависимость `io.github.stasbykov.justdotesting:scenario-plugin-api:1.0.0` из Maven Central. Для разработки плагина достаточно добавить зависимость из примера выше. При обновлении указывайте нужную совместимую версию SDK.

### Шаг 2. Реализуйте `ObjectBuilder`

Файл `src/main/java/example/order/OrderBuilder.java`:

```java
package example.order;

import com.fasterxml.jackson.databind.node.JsonNodeFactory;
import com.fasterxml.jackson.databind.node.ObjectNode;
import io.github.stasbykov.justdotesting.plugin.Field;
import io.github.stasbykov.justdotesting.plugin.ObjectBuilder;

import java.util.ArrayList;
import java.util.List;
import java.util.Optional;

public final class OrderBuilder implements ObjectBuilder {
    private static final JsonNodeFactory JSON = JsonNodeFactory.instance;

    @Override
    public Type type() {
        return new Type("order", "Заказ", 1, Format.JSON, false);
    }

    @Override
    public ObjectNode defaults() {
        return JSON.objectNode()
                .put("sku", "")
                .put("quantity", 1);
    }

    @Override
    public Form form(ObjectNode draft, Optional<Parent> parent,
                     Event event, String changedPath) {
        var fields = List.of(
                Field.input(Field.Kind.TEXT, "sku", "Артикул", true),
                Field.input(Field.Kind.NUMBER, "quantity", "Количество", true)
        );

        var issues = new ArrayList<Issue>();
        var quantity = draft.path("quantity");
        if (!quantity.canConvertToExactIntegral()
                || !quantity.canConvertToInt()
                || quantity.intValue() <= 0) {
            issues.add(new Issue("/quantity", "Количество должно быть целым и больше нуля"));
        }

        return new Form(draft, fields, issues);
    }

    @Override
    public Body generate(ObjectNode settings, Context context) {
        var json = JSON.objectNode();
        json.put("id", context.namedVariable().apply("uuidv7:order"));
        json.put("sku", settings.path("sku").asText());
        json.set("quantity", settings.get("quantity"));
        return new Body(json.toString());
    }
}
```

Здесь:

- `type()` задаёт неизменяемый технический ID `order`, имя в интерфейсе, версию **схемы настроек** `1`, формат `JSON` и отсутствие зависимости от родителя.
- `defaults()` возвращает первоначальные настройки нового объекта.
- `form(...)` создаёт поля редактора и сообщает об ошибках с помощью `Issue`. Полученный `draft` уже содержит изменения пользователя.
- `generate(...)` формирует итоговое тело. Приложение передаст его в маршрут объекта; сам конструктор ничего не отправляет.

Для текстовых тел вместо `Format.JSON` используйте `Format.TEXT` и возвращайте текст в `new Body("...")`.

### Шаг 3. Добавьте точку входа `BuilderPlugin`

Файл `src/main/java/example/order/OrderPlugin.java`:

```java
package example.order;

import io.github.stasbykov.justdotesting.plugin.BuilderPlugin;
import io.github.stasbykov.justdotesting.plugin.ObjectBuilder;
import java.util.List;

public final class OrderPlugin implements BuilderPlugin {
    @Override
    public List<ObjectBuilder> builders() {
        return List.of(new OrderBuilder());
    }
}
```

Именно `BuilderPlugin` приложение находит при загрузке JAR. Если потребуется несколько типов объектов, верните их все из `builders()` — по аналогии с примером «Доставка».

### Шаг 4. Зарегистрируйте плагин

Создайте файл **с точным именем**:

```text
src/main/resources/META-INF/services/io.github.stasbykov.justdotesting.plugin.BuilderPlugin
```

Его содержимое — одна строка с полным именем класса точки входа:

```text
example.order.OrderPlugin
```

Регистрация выполняется через Java `ServiceLoader`. Класс должен быть доступным (`public`) и иметь публичный конструктор без аргументов (если он не объявлен явно, компилятор создаст его).

Создайте `src/main/resources/META-INF/MANIFEST.MF`:

```text
Manifest-Version: 1.0
Jdt-Plugin-Id: example.order
Jdt-Plugin-Name: Заказы
Jdt-Plugin-Version: 1.0.0
Jdt-Plugin-Api: 1
```

Значения атрибутов:

| Атрибут | Значение |
| --- | --- |
| `Jdt-Plugin-Id` | Постоянный уникальный ID **плагина**, общий для всех типов внутри JAR. |
| `Jdt-Plugin-Name` | Название модуля в интерфейсе. |
| `Jdt-Plugin-Version` | Версия выпуска самого JAR, например `1.0.0`. |
| `Jdt-Plugin-Api` | Версия контракта приложения с плагинами. В текущем формате — `1`. |

**Не путайте ID плагина и ID типа:** `example.order` — модуль, `order` — один из его типов. Сохранённые проекты опираются на эти значения; не меняйте их при обычном обновлении плагина.

### Шаг 5. Соберите и установите JAR

Из каталога своего проекта:

```bash
mvn clean package
```

Скопируйте `target/order-builder-1.0.0.jar` в каталог модулей из меню **☰ → Модули… → Открыть каталог модулей**, перезапустите Just Do Testing и создайте объект «Заказ».

Для проверки можно ввести артикул `ABC-123` и количество `2`. Сгенерированное тело будет **примерно** таким (значение `id` вычисляется приложением):

```json
{
  "id": "019...",
  "sku": "ABC-123",
  "quantity": 2
}
```

Это законченный минимальный конструктор. Следующие разделы понадобятся для форм с зависимостями, более сложной генерации и обновления версий.

## Описание формы и её поведения

### Поля `Field`

SDK описывает форму декларативно. В `form(...)` возвращайте `List<Field>` в нужном порядке; приложение само отобразит элементы.

| Вид | Создание | Для чего |
| --- | --- | --- |
| `TEXT` | `Field.input(Field.Kind.TEXT, ...)` | Строка |
| `NUMBER` | `Field.input(Field.Kind.NUMBER, ...)` | Число |
| `CHECK` | `Field.input(Field.Kind.CHECK, ...)` | Флажок |
| `CHOICE` | `Field.choice(...)` | Выбор одного значения из списка |
| `GROUP` | `Field.group(...)` | Визуальная группа других полей |
| `ROWS` | `Field.rows(...)` | Редактируемый массив строк с заданными полями |

Пример выпадающего списка:

```java
Field.choice("priority", "Приоритет", List.of(
        new Field.Option("normal", "Обычный"),
        new Field.Option("urgent", "Срочный")
), true);
```

Приложение хранит **значение** (`normal`), а пользователю показывает **подпись** («Обычный»). При изменении подписи сохраняйте техническое значение прежним.

Пример редактируемого массива `items`:

```java
Field.rows(
        "items",
        "Позиции",
        JsonNodeFactory.instance.objectNode().put("quantity", 1),
        List.of(Field.input(Field.Kind.NUMBER, "quantity", "Количество", true))
);
```

Здесь `rowDefaults` описывает новую строку, а `quantity` относится к **текущей строке**, не к корню. `Field.group(...)` служит только для группировки: она не создаёт дополнительный вложенный уровень в JSON.

Поле «только чтение» создаётся через полный конструктор `Field` с `editable=false`; рабочий пример — `mode` в [ShippingPlugin.java](examples/shipping-builder/src/main/java/example/shipping/ShippingPlugin.java). Чтобы скрыть поле, не включайте его в возвращаемый список. Скрытое значение может остаться в `settings` — удалять его или включать в генерацию решает разработчик конструктора.

### Когда вызывается `form(...)`

`form(ObjectNode draft, Optional<Parent> parent, Event event, String changedPath)` возвращает `Form(settings, fields, issues)`.

| Событие | Ситуация | Поведение конструктора |
| --- | --- | --- |
| `OPEN` | Создание, повторное открытие объекта, подготовка сценария | Привести сохранённые настройки к корректному состоянию и построить форму. |
| `EDIT` | Пользователь меняет поле, добавляет или удаляет строку | Обработать новое значение и пересчитать зависимые поля. |
| `PARENT` | Выбран другой родитель, связь снята или родитель изменён | Обновить зависящие от родителя значения и набор вариантов. |

При `EDIT` путь изменённого поля передаётся как **JSON Pointer**, например `/items/0/quantity`. Для `OPEN` и `PARENT` он может быть пустым.

**Обязательное правило:** повторный `form(...)` с одинаковыми входными данными должен возвращать одинаковое состояние. Не создавайте в нём случайные ID, не обращайтесь к внешним сервисам и не меняйте независящие от события пользовательские значения. Для обновления зависимых полей возвращайте изменённый `draft` внутри `Form`.

### Валидация

Приложение проверяет обязательность, тип видимых полей и допустимость выбранных значений. Дополнительные бизнес-ограничения описывайте через `Issue(path, message)`:

```java
new Issue("/items/0/quantity", "Количество должно быть положительным")
```

`path` — JSON Pointer до проблемного значения, `message` — понятное пользователю объяснение. В процессе ввода числовое поле может временно содержать строку вроде `"1."`, поэтому проверяйте тип перед арифметическими операциями.

Объект с ошибками можно сохранить как черновик, но предпросмотр и выполнение требуют валидной формы.

## Зависимость от родительского объекта

Тип с `acceptsParent=true` позволяет пользователю выбрать другой объект проекта. Это удобно, когда доступные параметры дочернего объекта зависят от справочника, профиля, конфигурации или другого набора данных.

**Сценарий из примера «Доставка»:** у склада есть `zone=city` или `zone=remote`. Форма партии использует эту настройку, чтобы предлагать «Курьер»/«Перевозчик» и только подходящие услуги. При смене зоны недопустимый ранее выбранный вариант заменяется допустимым.

Что получает конструктор в `Optional<Parent>`:

| Поле | Смысл |
| --- | --- |
| `id()` | UUID родителя (связь не зависит от имени и папки) |
| `name()` | Имя для отображения |
| `pluginId()` и `typeId()` | Идентификаторы плагина и типа родителя |
| `version()` | Версия настроек родителя |
| `values()` | Копия сохранённых настроек родителя в формате `JsonNode` |

У ручного JSON-объекта `pluginId()` пуст, `typeId()` равен `json`, а `values()` содержит введённое JSON-дерево. У ручного текстового объекта тип `text` и значение является строкой. Если родитель не выбран либо его JSON не удалось разобрать, в форму может прийти `Optional.empty()`.

Проверяйте `pluginId`, `typeId`, `version` и существование нужных значений, прежде чем применять правила. При неизвестном типе или неполных данных используйте понятное состояние по умолчанию. Не допускайте потери корректного ручного выбора только из-за повторного открытия формы.

**Ограничения связи:** выбрать самого себя или своего потомка нельзя. Родитель **не выполняется автоматически**, и его генератор не вызывается при редактировании дочернего объекта. В `generate(...)` родитель уже не передаётся: всё, что нужно для итогового тела, сохраните в возвращаемых настройках на этапе `form(...)`. Объект и его маршруты настраиваются независимо.

## Генерация тела и переменные

Метод `generate(ObjectNode settings, Context context)` вызывается после успешной валидации и возвращает `Body`:

```java
return new Body(json.toString()); // JSON
// или
return new Body("Произвольный текст"); // TEXT
```

`Context` предоставляет:

- `iteration()` — номер итерации, начиная с `1`;
- `namedVariable().apply("uuidv7:order")` — значение именованной переменной текущего запуска;
- `checkCancelled()` — проверку запроса отмены при длительных вычислениях.

Сгенерированный объект создаётся **один раз на итерацию**, даже если у объекта несколько маршрутов. У предпросмотра отдельный контекст. Тело из `Body` передаётся буквально; не рассчитывайте, что приложение дополнительно обработает шаблонные строки внутри результата генератора. Если нужен согласованный идентификатор, используйте `namedVariable()` прямо при построении результата. То же именованное значение доступно в шагах маршрута по синтаксису `{{uuidv7:order}}`.

Для JSON-тела поля объекта можно использовать в шагах через JSON Pointer, например `{{/items/0/quantity}}`. Эти подстановки выполняет приложение на стороне маршрутов, не SDK.

**Важные ограничения:** генерация должна быть локальной и короткой. Для долгих циклов периодически вызывайте `context.checkCancelled()`. Приложение ограничивает один вызов генератора **10 секундами**. При ошибке генерации выполнение транспорта для этой итерации не начинается; ошибка отражается в журнале.

### Маскирование конфиденциальных данных

Можно отметить пути, значение которых не должно отображаться в предпросмотре, журнале или Allure:

```java
return new Body(json.toString(), List.of("/customer/phone"));
```

Для маскирования всего тела используйте `List.of("")`. **Маскирование влияет на отображение, но не изменяет тело, передаваемое транспорту.** Настройки формы сохраняются в проекте и могут попадать в экспорт — не храните в них пароли, токены и другие секреты.

## Версии и обновление плагина

У плагина есть **три независимых версии**:

| Версия | Где указана | Когда меняется |
| --- | --- | --- |
| **Версия плагина** | `Jdt-Plugin-Version` в манифесте | При выпуске нового JAR |
| **Версия настроек типа** | Третий аргумент `new Type(..., version, ...)` | Если меняется формат сохранённых настроек типа |
| **Версия API** | `Jdt-Plugin-Api` в манифесте | При переходе на другой поддерживаемый контракт приложения |

При изменении структуры настроек увеличьте `Type.version()` и переопределите `migrate(int from, ObjectNode settings)`:

```java
@Override
public ObjectNode migrate(int from, ObjectNode settings) {
    if (from == 1) {
        settings.put("quantity", settings.path("count").asInt(1));
        settings.remove("count");
        return settings;
    }
    if (from == type().version()) {
        return settings;
    }
    throw new IllegalArgumentException("Версия настроек " + from + " не поддерживается");
}
```

Это пример перехода с версии `1` на `2`, где поле `count` переименовали в `quantity`. Сам `type()` в таком случае должен возвращать версию `2`. Если переходов несколько, обработайте каждый поддерживаемый исходный формат. Плагин получает копию настроек; изменение файла проекта происходит при последующем явном сохранении.

Стандартная реализация `migrate` допускает только текущую версию. **Стабильные `Jdt-Plugin-Id` и `Type.id()` не меняйте**, иначе приложение не сможет сопоставить сохранённое определение с новым конструктором.

Если плагин отсутствует, проект можно открыть, сохранить или экспортировать, сохранив исходное определение объекта; другие объекты и сценарии остаются доступными. Для восстановления работы конструктора установите совместимый JAR.

## Тестирование и рекомендации

Конструктор — обычный Java-код, поэтому его правила удобно тестировать без JavaFX и запущенных Kafka/БД. Минимальный набор проверок:

1. `ServiceLoader.load(BuilderPlugin.class)` находит точку входа, а `builders()` возвращает ожидаемые типы без дублирующихся ID.
2. `defaults()` и `form(..., Event.OPEN, ...)` возвращают корректные начальные значения.
3. После `EDIT` пересчитываются зависимые поля, при этом допустимый ручной выбор сохраняется.
4. После `PARENT` изменение или удаление родителя приводит к ожидаемому набору вариантов.
5. Для ошибочных настроек возвращаются `Issue` с верными путями, а для валидных `generate(...)` создаёт JSON/текст нужного формата.
6. При изменении схемы `migrate(...)` корректно обрабатывает предыдущие версии.
7. Отдельно проверяются пустые массивы, некорректные типы и отмена длительной генерации.

Тесты из [shipping-builder](examples/shipping-builder/src/test/java/example/shipping/ShippingPluginTest.java) — отправная точка. Для проверки JSON удобен `ObjectMapper.readTree(...)`, а для генерации можно передать тестовый `new Context(1, key -> "test-id")`. Так тест не зависит от случайных идентификаторов.

Рекомендации по реализации:

- Не помещайте пользовательскую бизнес-логику в `BuilderPlugin`: это только точка входа. Основные правила держите в соответствующем `ObjectBuilder`.
- Держите `form(...)` и `generate(...)` детерминированными относительно переданных настроек и контекста; не выполняйте в них сетевые запросы и другие побочные действия.
- Используйте стабильные машинные значения `Field.Option` и понятные русские подписи/ошибки.
- Не сохраняйте динамическое состояние пользователя в полях singleton-класса конструктора; приложение может вызывать один экземпляр для разных объектов.
- Собственные сторонние зависимости, отсутствующие в приложении, включайте в JAR (например, через Maven Shade Plugin). При совпадении пакетов применяйте relocation. Не упаковывайте внутрь вторую копию SDK. Для каждого JAR предусмотрен отдельный загрузчик классов с общим API от приложения.
- Устанавливайте только доверенные плагины: код JAR выполняется с правами процесса приложения.

## Установка и решение проблем

Каталог плагинов удобнее открывать из интерфейса: **☰ → Модули… → Открыть каталог модулей**. Стандартные расположения:

| ОС | Каталог |
| --- | --- |
| Linux | `~/.just-do-testing/plugins/` |
| Windows | `%USERPROFILE%\.just-do-testing\plugins\` |

После добавления, замены или удаления JAR **перезапустите приложение**.

Если конструктор не появился:

1. Откройте **☰ → Модули…** и посмотрите статус и сообщение об ошибке.
2. Проверьте содержимое JAR: есть ли файл `META-INF/services/io.github.stasbykov.justdotesting.plugin.BuilderPlugin` и корректный класс в нём.
3. Убедитесь, что у класса `BuilderPlugin` есть публичный конструктор без аргументов.
4. Проверьте атрибуты `Jdt-Plugin-Id`, `Jdt-Plugin-Name`, `Jdt-Plugin-Version` и `Jdt-Plugin-Api` в `META-INF/MANIFEST.MF`.
5. Уберите старые и дублирующиеся JAR. Если два файла объявляют одинаковый `Jdt-Plugin-Id`, оба считаются конфликтующими.
6. Убедитесь, что плагин собран под Java 21, использует совместимую версию API и что все его дополнительные библиотеки доступны при загрузке.

Проверить, что необходимые метаданные действительно попали в сборку, можно командой:

```bash
jar tf target/order-builder-1.0.0.jar
unzip -p target/order-builder-1.0.0.jar META-INF/MANIFEST.MF
```

Если Maven не находит `scenario-plugin-api`, убедитесь, что указан артефакт `io.github.stasbykov.justdotesting:scenario-plugin-api:1.0.0`, Maven Central доступен и в настройках Maven нет блокирующего зеркала или офлайн-режима.

## Для сопровождающих SDK

Исходники API расположены в [`src/main/java/io/github/stasbykov/justdotesting/plugin`](src/main/java/io/github/stasbykov/justdotesting/plugin). Изменения проверяются CI вместе с примером. Push в `main` и pull request запускают проверки; Dependabot отслеживает Maven-зависимости и GitHub Actions.

Для выпуска версии обновите `revision` в корневом `pom.xml`, `sdk.version` в POM примера и версии в документации. После успешного CI создайте GitHub Release с тегом `vMAJOR.MINOR.PATCH`, указывающим на коммит из `main`. Workflow проверит соответствие версии, подпишет и опубликует SDK (включая исходники и Javadoc) в Maven Central, а затем прикрепит JAR примера к релизу. Публикация требует заранее настроенного GitHub Environment `maven-central` с учётными данными Central Portal и GPG для подписи.
